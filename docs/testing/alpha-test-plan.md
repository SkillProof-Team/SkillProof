# Alpha 测试计划

关联 [Issue #12（Alpha 测试计划、集成测试与报告）](https://github.com/SkillProof-Team/SkillProof/issues/12)。初版由 hope3243 于 2026-11-01 编写，本轮验收由 SeanYuanWSY 负责。

## 本轮范围与顺序

本轮覆盖注册登录、岗位选择、答题保存、提交评分和结果展示。学习建议、历史对比等 P1 功能暂不纳入。执行结果统一记录在[测试报告](alpha-test-report.md)。

| 顺序 | 测试范围 | 前置条件 |
| --- | --- | --- |
| 1 | 数据库、认证和岗位接口 | 后端能够启动，使用独立测试数据库 |
| 2 | 创建测评、保存与提交、评分和报告查询 | 测试题库符合每维两道简单题、一道中等题的规则 |
| 3 | 注册登录、岗位选择与答题页面 | 对应页面能连接受测后端 |
| 4 | 结果图表与完整页面流程 | 结果路由已接入，能使用提交后的报告 |
| 5 | 最终 main 回归 | 页面完成整合，按正式题库当前状态检查可用性 |

## 开始前要确认的事项

1. **题库发布状态。** 草稿可以保留在正式题库中，只有复核后标为 `published` 的题目参与抽题。检查当前状态：已发布题目充足时创建成功，不足时应明确拒绝，不能把草稿当作已发布题目使用。
2. **抽题规则。** 已合并的测评约定为每维两道简单、一道中等，共 18 题，只从已发布题目中抽取；验收时核对六维题量、难度、不重复及题库不足的处理。纯评分中的困难题样例用于验证评分函数对历史快照的支持，当前新建测评不抽困难题。
3. **受测版本。** 待合并 PR 先同步最新 main，处理冲突，并登记本次必测项。每次执行记录 PR 和完整提交版本；修复或集成改变相关代码后，复测受影响项目。临时组合分支的结果不记成最终 main 验收结果。

业务测试使用独立、固定的测试题，覆盖全草稿、已发布题量不足和题量充足的情况。正式题库另行检查格式、题号、答案与来源要求，不固定题量或发布状态；题库更新不需要重写这些业务测试。

依据：[题库数据](../../backend/app/content/questions.json)、[题库清单](../../backend/app/content/manifest.json)、[人工复核记录](question-bank-review.md)、[API 契约](../design/api.md)、[评分约定](../design/scoring.md)。

## 测试步骤

按 README 准备依赖，使用独立测试数据库和两个测试账号，按上表顺序执行。功能未接好的部分记为“阻塞”。

**01 启动项目**

安装依赖，运行前端 lint/build，启动前后端并访问健康接口。重复初始化数据库，检查已有数据没有被覆盖；检查题库数量和格式与说明一致。

**02 注册和登录**

账户接口接好后，注册新账号，退出后重新登录，再刷新页面。应能恢复正确身份，退出或会话过期后不能访问私有数据。另试重复注册、错误密码、空值及姓名和密码长度边界，应有错误提示，响应不包含密码或哈希。

**03 选择岗位、创建测评**

登录且题库可用后，选择开放岗位，创建测评，再重复点击创建。应恢复同一份进行中测评，题量、六维和难度符合确认的规则，响应不含正确答案和解析。未开放岗位或题库不足时应拒绝创建，不留下不完整记录。

**04 答题和保存**

进入测评，分别做单选、多选，切题、保存、清空一题，再刷新并重新进入。已保存答案应能恢复，进度正确。另通过接口提交非法题号、选项和错误数据类型，应被拒绝，原草稿不变。

**05 提交测评**

先在未答完时提交，应提示无法提交且保留草稿。全部答完并保存后再提交，应保存状态、时间和结果。重复及并发提交只评分一次，提交后不能改答案；模拟评分失败时草稿仍保留。之后再次测评，应生成新记录且保留旧结果。

**06 核对评分和结果**

评分接好后，用已知答案检查全对、全错、多选漏选和选错；多选须全部选对才得分，选项顺序不影响结果。按确认的规则手算综合分、六维分数、精度及薄弱项排序。另用“30 题、某维 5 题全对”的样例检查该维为 100 分。网页、接口和数据库应一致，修改当前题库不应改变原题卷或已存报告。

**07 检查权限和异常**

准备账号 A、B，用 B 获取、修改、提交 A 的测评或查询 A 的报告，应被拒绝。未登录、缺少或使用其他会话的 CSRF、查询不存在或未提交的报告也应按接口约定处理。页面测试保存失败、提交响应丢失、重复点击和重试，应有提示且不重复生成结果。

**08 完整操作和重启**

页面接好后，在浏览器完成注册→登录→选岗位→答题→保存刷新→提交→结果，检查报告页能直接打开和刷新，桌面与手机宽度下显示正常。正常关闭服务后保留数据库，再启动并登录，草稿和报告应仍在。

## 自动化和记录

复用已有测试，QA 核对业务覆盖、补充遗漏，并负责最终整合验收。开发者随功能 PR 交付对应测试与必测登记；已经合入 main 的功能，其补充测试由 QA 任务交付。完整流程所需功能必须包含在受测版本中。

`backend/tests` 检查后端模块，`tests/acceptance/test_*.py` 检查接口业务，`tests/e2e/test_*.cjs` 检查页面和完整流程。每个 PR 只登记本次必测用例，CI 仍运行全部已有测试与新增测试。

共享测试题由 `tests/support/question_bank.py` 生成到临时目录；正式题库由 `test_question_bank_content.py` 单独校验。成功流程、题库不足等用例自行准备所需状态，不依赖当天正式题目是否发布。

浏览器组通过 unittest 接入统一入口与必测登记，每组必须完整运行并通过；新增浏览器文件会自动发现，无需逐项修改 CI。缺少页面或前置功能时不能跳过后算作通过。

用例写明前置条件、操作和预期；每轮统一记录日期、执行人、完整版本、环境与实际命令，不逐条重复。自动化保存逐项结果及必要截图、日志；手动检查补记实际结果，标为“通过／失败／阻塞／未执行”。发现问题建立 Bug Issue，修复后复测并保留原失败记录。

测试报告汇总结果、问题与未执行范围；[执行记录](evidence/alpha-execution-record.txt)固定维护一份，按时间追加版本、命令和输出摘要，不按日期新建文件。原始日志与截图按每次运行保存。未执行项目不计为通过。最终交付版本再做完整回归，经另一名成员 Review 后交付。
